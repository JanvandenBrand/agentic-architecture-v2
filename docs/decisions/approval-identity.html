Approval identity in Agentic Architecture v2

A design discussion about what an AFF human approval actually proves, and what it should prove.

Date
4 September 2026
Repository
aramsmith/agentic-architecture-v2
Scope
Solo architect topology
Schema impact
None

Tool 1.3.0 clarification

The discussion below is a historical design record, not the current operating procedure. Key identity now comes from verified signature data, and cross-key transitions require predecessor-key authorisation. A rotation declaration alone is insufficient; lost-key recovery is blocked. New decisions are published without replacing previous files. The first case key still needs independent human fingerprint verification; signatures and local policy do not prove personal identity or isolate signing from an agent with file access.

Use the current contract guidance and tool upgrade note. Neither historical schema version is rewritten, and optional deployment authorisations remain blocked.

Why this discussion happened

A full audit of the repository produced one finding that outranked the rest. The framework's headline claim is human-final governance — the human architect owns every material decision and approves every phase. The machinery does not support that claim.

An approval record's approver field is defined in the schema as { "type": "string", "minLength": 1 }. The validator reads it and never checks it against anything. "Human architect" and "z" are equally valid.

The proof already sits in the repository

The Contoso smoke harness programmatically writes an approval record. It is schema-valid. Its hashes converge with both reviewer records. It passes every check in the validator. It says "decision": "APPROVED". No human touched it.

It is benign only because it volunteers three labels saying so — syntheticTestEvidence, realApproval: false, and an approver string beginning "Synthetic Test Human". Remove those voluntary declarations and it is indistinguishable from a real approval.

Compounding this: AFF-0 holds edit and execute on the case folder. The operating contract states that agents cannot approve for the human. That is prose. Nothing enforced it.

What the discussion changed

Two positions were tested and abandoned during the conversation. Recording them matters as much as recording the conclusions.

Positions revised in the course of the discussion
Initial positionWhy it was wrongReplaced by
If cases never leave the laptop, identity is close to worthless. Framed against the wrong threat. The question is not whether the architect is honest — they are, and they own everything. The question is what stops an agent writing the approval. Identity is worth having precisely because agents hold write access to the case.
Add a second human reviewer for four-eyes assurance. Two unverified name strings are worth what one is. With genuinely one architect available, a mandatory second approver produces a rubber stamp — a control that reliably fails while appearing to pass. Team topology deferred entirely. Duo review would come free with a shared repository, and is unavailable and unhelpful without one.

Topology — settled first, because everything depends on it

Three deployment patterns were considered: a solo architect on a laptop; a team working in a forked repository; and a mix.

The team pattern was forbidden by the framework's own contract

A team needs somewhere to share case state. .gitignore excludes cases/*; the operating contract says "Case data is local-only and must not be committed or pushed"; the README says "never commit or push it". A forking team has no supported mechanism at all — divergent private case folders, a broken append-only journal, and no convergence.

Decision: solo only. Cases stay off GitHub because they may contain sensitive data. The team pattern is deferred to a later version rather than left as an unbuilt aspiration.

This has a direct consequence. In a shared repository, GitHub would already solve identity — a merged pull request approved by a named account under branch protection is stronger and better audited than any key managed on a laptop. That option is not available here, so the identity has to be built.

The core principle

Verification, not access control

The instinct is to stop agents writing the approval file. That cannot be enforced: agents run as the same Windows user, and file permissions are per-user — an ACL that blocks the agent blocks the human too. A read-only attribute is removed with one command.

So the problem is inverted. Anything may write an approval; only a correctly signed one counts. This is exactly the pattern the framework already uses for artefacts: edits are not prevented, they are made to fail validation. The same idea, applied one level up — from artefacts to decisions.

Mechanism, verified before adoption

The load-bearing claim — that an agent reading the key file gains nothing — was tested rather than assumed:

key file starts:              -----BEGIN ENCRYPTED PRIVATE KEY-----
ciphertext on disk:           true
sign without passphrase   ->  blocked
wrong passphrase          ->  blocked
correct passphrase        ->  signed, verify = true
tampered payload          ->  verify = false

Node 26.5.1 supports Ed25519 key generation, passphrase-encrypted private keys, and detached signing natively. The repository currently has no cryptography dependency and needs none. Signing reuses json-canonicalize, already present and already trusted for hashing.

Why the signature covers the whole record

Signing only the artefact hashes would leave the verdict unprotected. A valid signature over a hash set could be lifted and attached to a modified record — flipping REJECTED to APPROVED, changing the phase, or backdating the decision — and it would still verify. The evidence would be cryptographically signed while the decision was not.

Why display must derive from verification

If the rendered views read the claimed mode, the control is theatre: an agent writes approvalMode: "human-verified" with no signature, and the solution overview displays "Human verified". The label must be the result of checking, never the assertion being checked.

The agent then reads the approval, but the gate is npm run validate: signature valid, fingerprint matching the trusted key, hashes converged, predecessor phase approved. An agent that fabricates an approval produces a record with no valid signature, and validation fails.

Accepted limits

Delegation is permitted. If the architect types the passphrase because an agent asked, that is authority exercised, not forgery. No system prevents an authorised person from delegating. What the design does is make the act deliberate, one phase at a time, with the evidence on screen.

A determined agent could still rebuild a forged history by overwriting the key store and re-signing every approval — there is no external anchor on a single laptop. But that moves forgery from writing one JSON file to destroying the architect's identity file and regenerating the entire chain: conspicuous and detectable rather than trivial. For solo work, that is the right ceiling.

Removing every signature from a case was not detectable in the first signing build. Continuity protected a case that still held a verified decision, but stripping them all left records that looked as though the case was never signed. This was found by test rather than reasoning, and closed by a per-machine policy: creating an approval key sets requireSignedApprovals, so an unsigned real decision fails on that machine. A machine that has never held a key has no expectation to measure against, so the offline evaluation is unaffected.

The passphrase must never be typed into an agent conversation. An agent that asks for it is phishing, whether or not it intends to be.

Implementation note discovered during build

The agreed display target was "both phase HTML and the solution overview". Phase HTML is generated by the phase agent before review and approval exist, so there is no approval to show. Worse, adding approval state to it later would change the document's hash and invalidate the approval bound to it — a circular dependency. The solution overview carries the per-phase mode; the phase document instead states plainly that it is generated evidence carrying no approval.

Deferred, deliberately

  • Team topology — forking, shared cases, GitHub-backed identity and PR-based duo review. Requires replacing the blanket ban on committing case data with a data-classification rule.
  • Deployment authorisation — Phases 7 and 8 declare prerequisites (scoped-attempt-authorisation, scoped-test-attempt-authorisation, phase-7-succeeded) that have no record type. They currently fail closed. Building them needs schema contract 1.0.0 → 1.1.0.
  • Proof the architect read the evidence — a confirmation token derived from the converged hashes. Deferred until there is evidence the control is needed.
  • Separate Windows account for agents — the only hard write-prevention boundary. Rejected as disproportionate for solo work.

Still open from the audit

One item remains unaddressed and is knowingly accepted for now: the validator proves the internal consistency of the current working tree, not the immutability of history. There is no hash chain, signature over the record sequence, or external anchor. Increment B narrows this for approvals specifically; it does not close it for the case as a whole.
